# Prototype Instructions

## Execution efficiency

- Treat one user request as one prototype iteration. Batch internal code edits and review findings before the required production build; do not rebuild or relaunch after every micro-patch.
- For a localized browser-loading bug, reproduce it once, identify one primary cause, make the smallest viable change, then verify the reported URL plus one representative similar page. Add one failure/recovery check only when that path was changed.
- Do not repeat the same navigation, build, or desktop launch unless the code changed or the prior result was inconclusive. Once the target behavior and representative regression pass, stop.
- Do not expand a localized fix into a broad readiness, history, security, or performance redesign unless direct evidence shows the broader change is necessary. Record non-blocking edge cases instead of extending the task.
- Do not use subagents or multi-round cross-review unless the user explicitly requests delegation. Keep code inspection focused on the touched functions and their immediate callers.
- If a supposedly simple task is likely to exceed 20 minutes or touch more than two core modules, pause and tell the user why before proceeding.

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

After every user-directed code or visual iteration, always run the normal production build so `dist` and the desktop prototype reflect the latest source. Do not run smoke suites or other automated tests unless the user explicitly asks; confirm the requested result through implementation and the available preview instead.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

- Keep `Brizo.command` as the current branded, double-clickable macOS launcher; retain `Bean.command` only as a backwards-compatible launcher so existing user shortcuts do not break.
- The desktop test window must load `dist/client/index.html` directly through Electron and must not depend on Vite or another local web server.
- Preserve `npm run desktop:smoke` as the automated check for the local-file desktop runtime.
- External web pages in the desktop prototype must use an isolated Electron `WebContentsView`; keep Node integration disabled, context isolation and sandboxing enabled, and remote permission requests denied by default.
- Preserve `npm run desktop:browser-smoke` as the automated external-page runtime check.

It reuses or starts the Vite server at `http://127.0.0.1:5173/`, launches a standalone Electron window against that URL, and keeps renderer changes under `src/` visible without rebuilding `dist` or restarting the application.

## Brizo product direction

- Do not introduce a Mission, project-space, task-space, or similar organizational object. Brizo must infer useful context from the current page, selected tabs, recent normal-profile activity, bookmarks, and explicit user input without asking users to create or manage work containers.
- Product priorities, in order, are: search-result quality and speed; practical and stable Use execution; focused ambient assistance such as secure username/password help and webpage analysis; distinctive visual craft; then conventional browser utilities. Do not expand the product by adding more top-level modes, dashboards, or organizational workflows.
- Make Brizo feel as though it understands the user while requiring as few clicks and decisions as possible. Resolve low-risk, reversible choices automatically; ask only when ambiguity materially changes the result or an action has meaningful external, privacy, credential, financial, deletion, or communication impact.
- The core product feeling is that the browser recedes into the background: search should return an immediately useful answer, webpage intelligence should appear just in time, and Use should complete real work reliably without forcing users to manage plans, agents, or intermediate state.
- Preserve a small number of deliberate “wow” moments that reveal genuine intelligence rather than visual novelty alone, especially instant cross-page understanding, automatic organization, context-aware credential assistance within the existing `safeStorage` security boundary, and visible recovery from a Use failure.
- Brizo must look and feel materially different from Chrome while remaining calmer and simpler than feature-heavy browsers. Visual distinction may never compromise startup time, interaction latency, memory pressure, battery use, or webpage performance.
- Treat fast startup, low idle overhead, low memory/CPU pressure, and fast perceived search/Use progress as product features with explicit budgets and regression checks, not as late-stage optimization work.
- Let the idle new-tab particle plane flow only during its short entrance or a genuine focus return, then retain its final static frame without a background timer. Preserve the Ask Sparkles draw-in and staggered soft loop through focus-aware sampled states rather than a continuously running CSS animation, because a permanent compositor animation is not acceptable in Brizo's transparent desktop window.
- Add one local-first intelligent page-cleanup layer for cookie-consent banners, network ads, interstitials, floating/sticky edge ads, side-rail ads, newsletter/app-install prompts, and other verified nuisance overlays. Use deterministic filter lists and conservative DOM heuristics before any model-based technique, collapse vacated ad space, and reflow the remaining page cleanly without creating ongoing per-page model, CPU, or GPU cost.
- Cookie automation means choosing consent-banner options according to the user's saved preference, not inspecting or manipulating authentication cookies. Default to required cookies only, reject non-essential purposes when the banner supports it, remember per-site exceptions, fail closed when the banner cannot be identified confidently, and never treat a paywall, login, checkout, security, age-verification, or permission surface as a dismissible cookie prompt.
- Balanced cleanup is the default: block known ads and trackers, remove high-confidence nuisance overlays and side rails, expose one unobtrusive undo or per-site disable action, and preserve legitimate navigation, document sidebars, comments, media controls, login, checkout, subscription, and accessibility surfaces. Offer a stricter per-site mode, but never bypass a paywall or other access control.
- Put every ambient default and automatic-choice policy in one compact Settings system rather than scattering toggles across the browser. Keep the root menu concise and organize the full Settings panel into no more than six sections: 智能浏览, 搜索与 AI, 隐私与安全, 外观与性能, 下载与数据, and 关于. Use recommended presets plus progressive disclosure for per-site exceptions and advanced controls; do not flatten every option into the root menu.
- The 智能浏览 settings section owns cookie-consent behavior, ad/page cleanup level, contextual tab use, account suggestions, tab sleeping/duplicate handling, and proactive page analysis. Every automatic feature must show its current default, provide a reversible per-site override where relevant, and preserve the low-risk automatic / high-risk confirmation boundary.
